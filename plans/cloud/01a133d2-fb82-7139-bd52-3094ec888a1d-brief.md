## The task

Make the published search template (`views/search.pug`) pass `nera build --check`
with no `a11y-*` warnings when a site includes it in a page that brings its own
`h1`. Two changes, both **non-breaking (minor)**: the search input gets an
accessible name (`aria-label`, translatable through the site's `t()`, falling back
to "Search"), and the template's `h1.search__title` becomes **opt-out** through a
new config key `show_title` in `config/search.yaml` whose default keeps today's
markup exactly. Plus tests, README and a proposed CHANGELOG entry.

Issue text, verbatim:

```text
## Today

`@nera-static/plugin-search` 2.2.0 ships `views/search.pug`, which `npx nera-search` copies to `views/vendor/plugin-search/` (or the theme's vendor folder) and the site includes by hand. Its markup:

- `h1.search__title Search` — its own top-level heading;
- `input.search__input(type="search", placeholder="Search...", data-search-input, …)` — no `<label>`, no `aria-label`; a placeholder is not an accessible name.

## The problem

Every site that uses the template as published gets two warnings from `nera build --check` (`@nera-static/validate` ≥ 1.2.0, output pass):

- `a11y-h1` — the search page's layout or Markdown usually brings its own `h1`, so the page ends up with two;
- `a11y-form-label` — the search input has no accessible name.

Found 2026-10-12 while building the search recipe of the Nera skill (`nera-cli/skills/nera/recipes/search.md`, issue 01a1260d-8ec6-701e-98a0-816bd8ad9c4f) in a scaffolded site. The recipe works around it today: no `#` heading on the search page, and `aria-label="Search"` added to the site's copy.

## How it should work

The published template passes `nera build --check` without `a11y-*` warnings when included in a page whose layout has the page's `h1`:

- the search input gets an accessible name, translatable via the site's `t()` (e.g. a visually hidden `label(for=…)` or `aria-label=t('search_label')`, falling back to "Search");
- the template no longer forces an `h1`: drop it, or demote it / make it optional (e.g. a mixin parameter or a config key `show_title`).

## Semver

Template markup is a contract (users style the BEM classes). Adding an `aria-label` or a hidden label is additive → minor. Removing or demoting `h1.search__title` changes markup sites may style → **major**, with a `### Migration from v2.x` CHANGELOG section — unless it is made opt-out via a config key with today's default (minor). Decide while planning; prefer the non-breaking route.
```

### Plugin contract (from the workspace rules)

- A plugin exports synchronous hooks `getAppData({ app, pagesData })` → a **plain
  object** (the new `app`) and `getMetaData({ app, pagesData })` → an **array**.
  Keep them synchronous (see the comment above `getAppData` in `index.js`).
- Config is read from the **site** (`config/search.yaml` via `getConfig`, already
  done in `loadConfig()`); the file shipped in the package is documentation only.
  Every key needs a JS fallback; a missing config file must behave like today.
- Templates see `app`, `meta`, `content` and, inside a real build, a `t(key)`
  helper. Core builds `t` per page like this (`@nera-static/core` `src/render.js`):

  ```js
  data.t = (key) =>
      data.app.translations
          ? data.app.translations[pageData.meta.lang || data.app.lang]?.[key] || key
          : key
  ```

  So **`t` returns the key itself when no translation exists** — `t('search_label')`
  on a site without that key yields the string `search_label`, not `undefined`.
  The fallback to "Search" must detect that (result equal to the key, or empty).
  And `t` is **absent** when the template is rendered outside core (the existing
  template tests call `pug.renderFile` with only `app`/`meta`), so guard with
  `typeof t === 'function'`.
- Translations come from `app.translations[<lang>][<key>]` (a site's
  `config/app.yaml` / translation config). The key name to use is
  **`search_label`**.

### Semver classification (workspace rules)

- **minor**: a new config key with a sensible default when absent; a new
  `app.<key>` alongside existing ones; additive template attributes.
- **major**: template markup or BEM class names change (users keep copies under
  `views/vendor/plugin-search/` and style them). That is why the `h1` stays by
  default.
- So this issue is **2.3.0 (minor)**.

### The validator rules you must satisfy (`@nera-static/validate` 1.4.2, `src/output-rules.js`)

- `a11y-h1`: warns when a built page has **zero or more than one** `<h1>`.
- `a11y-form-label`: warns for an `input`/`select`/`textarea` (except
  `type` hidden/submit/button/reset/image) that has none of: a non-empty
  `aria-label`, `aria-labelledby`, an `id` matched by a `<label for>`, or a
  wrapping `<label>`.

### How a site uses the template (README "Usage", `nera new` scaffold)

A scaffolded site (`npx @nera-static/nera new site`) has
`theme/views/layouts/layout.pug` and `theme/views/pages/default.pug`; the layout
does **not** print an `h1` itself — the page's Markdown `# Heading` becomes the
`h1` inside `content`. A search page is typically:

```pug
//- theme/views/pages/search.pug
extends ../layouts/layout

block content
  main
    | !{ content }
    include /vendor/plugin-search/search.pug
```

with `pages/search.md` carrying `layout: pages/search.pug`, a `title`, and a
`# Search` heading.

## What to build

1. **`views/search.pug`**
    - Compute the label once: if `t` is a function and `t('search_label')` is a
      non-empty string different from `'search_label'`, use it; otherwise
      `'Search'`.
    - Add `aria-label=<label>` to `input.search__input`. Keep every existing
      attribute and class unchanged.
    - Wrap `h1.search__title Search` in a condition so it renders unless
      `app.searchShowTitle === false`. With no `app`, or the key absent, it
      renders exactly as today. Do not change the `h1` element, class or text.
    - Keep the existing comment style (`//-`).
2. **`index.js`**: `loadConfig()` reads `show_title` (default `true`; only an
   explicit `false` turns it off, mirroring how `group_by_lang` treats `true`), and
   `getAppData` returns it as **`app.searchShowTitle`** (boolean) alongside
   `searchIndexPath`/`searchIndexPaths`. No other output changes — the index files
   stay byte-identical.
3. **`config/search.yaml`**: document `show_title: true` with a comment in the
   style of the `group_by_lang` one (what it does; set `false` when the page
   brings its own `h1`, e.g. from the Markdown `# Heading`, so `nera build --check`
   reports one `h1`).
4. **Tests** (`test/search-client.test.js` "shipped search.pug template", and
   `test/plugin-search.test.js` for the hook):
    - renders with `aria-label="Search"` when no `t` is passed;
    - renders with `aria-label="Search"` when `t` returns the key (simulate core's
      `t` with no translation);
    - renders the translated label when `t('search_label')` returns e.g. `Suche`;
    - assert the accessible name **the way the validator does**: parse the
      rendered HTML (happy-dom is available) and check the input has a non-empty
      `aria-label` — that pins acceptance criterion 1;
    - `h1.search__title` is present by default (no `app`, and `app` without the
      key) and absent with `app.searchShowTitle: false`;
    - `getAppData` sets `searchShowTitle: true` with no config file and with
      `show_title` absent, and `false` with `show_title: false` (follow how the
      existing tests write a temp `config/search.yaml` and `chdir`).
5. **`README.md`**:
    - Configuration section: document `show_title`.
    - "Data exposed" section: add `app.searchShowTitle`.
    - Usage / template section: say the input carries `aria-label` from
      `t('search_label')` (fallback "Search") and how to translate it (a
      `search_label` key in the site's translations); show `show_title: false` for
      a page whose Markdown already has the `# Heading`, so the page has one `h1`.
    - Styling table: note that `.search__title` is only emitted while
      `show_title` is not `false`.
    - An upgrade note matching the existing "If your site published templates
      before upgrading…" paragraph: a vendored copy keeps the old markup;
      `npx nera-search --force` only if never edited, else add the two changes by
      hand (show them).
